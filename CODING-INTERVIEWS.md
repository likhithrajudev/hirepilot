# Coding interviews

Choose **Interview practice → Coding**. Karthik is assigned automatically. Select Python 3, JavaScript (Node.js), C++17, or Java and one to three problems. Difficulty selects three eligible challenges; the requested number is shuffled without repetition. All problems in a session share the existing single interview allowance charge. Other plan behavior is unchanged.

The room contains a problem statement, input/output examples, constraints, Monaco editor (with a plain-text fallback), language selection, source download, autosave, run examples, submit all tests, sequential advancement/explicit skipping, and normal voice/text conversation. Each language's source is retained independently. Optimistic versions reject conflicting tabs instead of silently overwriting code. Monitored sessions disallow paste and retain the existing integrity signals.

Nine tasks cover three difficulties. Each has two visible examples and at least four hidden cases, including empty input, duplicates, negative values, overflow-sized answers, nested boundaries, cycles, unreachable paths, and window-boundary cases as applicable. Test inputs and reference outputs are server-owned, not generated by an LLM. Candidate programs read stdin and write stdout; output comparison ignores whitespace between values. A finite passing suite is evidence, not a proof of correctness or complexity.

Technical interview metadata may request `workspace: "coding"`; the server chooses a reviewed task, opens the editor, and replaces the spoken introduction with the actual task title. Other interview types cannot create arbitrary coding tasks through metadata. In dedicated Coding mode the workspace exists before the opening AI prompt. Every follow-up receives the active statement, latest saved source/hash, and bounded recent execution summaries, including the tested source hash. The AI is told to stay on that problem, allow coding time, and distinguish saved tests from current edits. Next problem requires a successful full-suite run of the current source/language, or explicit skip.

Code and timestamped runs are included in candidate/admin reports. Writing code is enough to request a report even with no spoken answer. Reports wait for an active run; final editor saves precede report generation. Natural AI closure leaves a coding session writable until the client flushes the editor and calls finish. Saved artifacts become read-only after completion. Session deletion deletes workspaces and runs. Owners alone can edit/run; platform admins can review artifacts through the protected report, but cannot inject code into another candidate's workspace.

## Execution boundary

The API only sends a fixed-schema job to `CODE_RUNNER_URL` authenticated with `CODE_RUNNER_TOKEN`; it never executes candidate code or receives the Docker socket. The trusted controller accepts a language enum, bounded source, and bounded inputs. It cannot accept user-selected images, commands, Docker options, mounts, or URLs. Each job creates a new container from `hirepilot-code-runtime:local`, compiles once, and launches a fresh process for each test.

Child restrictions: non-root UID 65534, no network, no host mounts or Docker socket, read-only root, all capabilities dropped, no privilege escalation, 512 MB memory without swap, one CPU, 64 processes, bounded writable tmpfs, 2-second test runtime, 20-second compilation, 60-second total deadline, and bounded file/output sizes. Jobs accept up to 50 KB source and 500 KB total test inputs; payload arguments are split to respect operating-system argument limits. The controller removes each container on exit. Two controller jobs can run concurrently. API limits are ten run attempts per user/minute, one current run per interview, and 120 stored runs/interview.

**The trusted controller's Docker socket grants broad control over its Docker host.** Container restrictions on child jobs do not remove that control from the controller, and containers still share the host kernel. A dedicated execution host/VM and stronger sandbox runtime are appropriate for an internet-facing hostile-code service. The implementation is not a claim of VM-grade isolation.

## Local activation — authorized and running

The user explicitly authorized the local Docker-socket boundary, and the local controller is now running. Both runner services remain behind the `coding-runner` Compose profile so a new installation does not silently grant Docker access. The editor and setup check real runner availability and disclose outages.

To start the authorized local development runner:

```sh
docker compose --profile coding-runner up -d --build code-runner
docker compose up -d --build --no-deps backend frontend
```

Set a strong matching `CODE_RUNNER_TOKEN` before production. The checked-in fallback token is local-development configuration only. The controller has no published HTTP port and uses an internal network shared with the API. A separately hosted controller can instead be configured through the two environment variables, without giving the application host's Docker socket to a service.
